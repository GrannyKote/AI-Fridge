НИР 3. Синхронизация кладовой и списка покупок AI-Fridge

Запуск из корня AI-Fridge. При использовании ZIP распакуйте его содержимое в
research/nir3-sync. Скрипты не запускают приложение и не обращаются к рабочей БД.

1. python research/nir3-sync/checkout-check.py
   Нужны зависимости существующего бэкенда, включая httpx для FastAPI TestClient.
   Тест создаёт отдельный SQLite-файл во временном каталоге, проверяет его адрес,
   выполняет реальные обработчики HTTP через ASGI и в конце закрывает БД.
   C означает checkout, P чтение кладовой, L чтение открытого списка. Итоги (P,L)
   CPL=(1,0), PCL=(0,0), LCP=(1,1), PLC=(0,1). После каждой операции итог (1,0).

2. node research/nir3-sync/cache-check.mjs
   Нужны установленные зависимости frontend/app. Проверено на Node 24.12.
   Используется исходный модуль offlineStore.js, ожиданием двух ответов управляет тест.
   Из нового products и старого purchases получается (1,1), в обратном порядке (0,0).

3. python research/nir3-sync/experiment.py
   Достаточно Python 3.10+ со стандартной библиотекой. Перезаписываются только
   trials.csv и results.json в каталоге скрипта. Выход воспроизводится при тех же
   Python и zlib. Seed 481721. Основной режим gzip, проверка чувствительности identity.
   Встроенные проверки охватывают разделение полосы, целостность дельты, повтор,
   неверную базу, усечённый JSON и достижение результата в длинном окне.
   В сценарии 3.3 (exploratory_new_list) новый список содержит 8 или 32 позиции.
   Для обоих размеров используются одни и те же сетевые условия. Оценивается
   решение по исходному купленному товару. В отчёте и сводке отобраны результаты
   этих двух вариантов из прогона 21.11.2026.
   Раздел результатов вынесен отдельно и не участвует в подтверждении гипотезы.

Схема trials.csv
   trial — идентификатор парного сценария, общий для трёх протоколов и двух кодеков.
   rows, checkout — прежний размер кладовой и число купленных позиций.
   kbps, window_ms — доступная полоса и момент обрыва/решения.
   list_ready_ms, pantry_ready_ms — момент готовности HTTP-ответа к передаче.
   err_A/B/C — ошибка решения по списку (0/1).
   wait_A/B/C — минимум из времени первого верного ответа и длины окна, мс.
   finish_A/B/C — момент верного ответа при мысленном продолжении соединения.
   size_A/B/C — предложенные полные объёмы ответов с модельными заголовками, байт.
   mixed_A — на момент выбора успел обновиться только один ресурс.
   err_A_both — ошибка альтернативного правила с просмотром обоих ресурсов.
   A — два независимых ресурса, B — полный снимок, C — пакет одной транзакции.

AI-Fridge — проверка гипотезы о вычислении остатков и аналитики
============================================================

Варианты
--------
A — чтение остатков коррелированными подзапросами и подсчёт статистики в Python.
B — агрегация событий в SQL, составные и другие индексы; временные ряды
    агрегируются по date_bin. Python форматирует ответ и объединяет итоги.
C — те же индексы, сохранённые суммы потребления и списания по партии
    (остаток получается из quantity и этих двух полей), часовые агрегаты
    по партии и типу события. Неполные часы читаются из журнала. Триггеры
    обновляют проекции в той же транзакции. Списания группы сериализуются
    advisory-блокировкой на время распределения по составляющим лота.
    Записи журнала в экспериментальной схеме защищены от UPDATE, DELETE и TRUNCATE.

Что именно измерено
-------------------
FastAPI и реальные маршруты pantry, Pydantic-схемы, HTTP по loopback и PostgreSQL.
Для всех вариантов одинаковый сервис записи (распределение списания между
партиями и возврат API-ответа), с заменой чтения остатков и проекций в C.
Использована структура таблиц ORM. A содержит штатные индексы этой структуры.
Тестовое приложение подключает только pantry router, подменяет сессию и
не отправляет ключ идемпотентности. Авторизация, reverse proxy, фронтенд
и доставка фоновых уведомлений за пределами измерения.

На каждый масштаб и вариант отдельная база. Четыре синтетические группы,
384 обычные партии и одна отдельная партия для проверки гонки. В тестируемой
группе 19 открытых партий до теста гонки. Около половины событий относятся
к группе 1. История занимает 380 дней; добавлены записи на временных границах
и одна будущая отметка в каждом типе событий. Имена и единицы стабильны внутри
товара, количества представлены двоичными дробями. Закрытые партии размещают
историю вне выдачи кладовой. Часы зафиксированы на 2026-01-01 12:17:33.

Измерены профили 90/10 и 70/30 (чтения/записи), 4 HTTP-клиента в замкнутом
цикле, 2 повтора по 240 запросов на конфигурацию. Чтение поровну распределено
между кладовой и годовой статистикой, запись между потреблением и списанием.
Запросы перемешаны детерминированно, порядок вариантов развёрнут во втором
повторе. Новый процесс API на прогон, разогрев двумя чтениями перед стартом.
Наборы накапливают успешные записи между повторами (до 192 событий на вариант
и масштаб). Результаты p50/p95/p99 получены методом ближайшего ранга; при 24
записях каждого типа в профиле 90/10 p99 равен максимуму. Процентили отражают
проверенную конкуренцию четырёх клиентов в лабораторном сценарии.

CPU — процессорное время процесса FastAPI за прогон, память — максимум
working set процесса FastAPI с момента его запуска, включая разогрев.
Счётчики блоков PostgreSQL собирались для каждой базы после задержки
публикации статистики. blks_read — чтения блоков вне shared buffers, которые
могут обслуживаться кэшем ОС. Планы вставки снимаются с последующим rollback.
Отдельный замер WAL проводился после нагрузки: разность глобального LSN
до и после одиночной вставки (включая её триггеры, до отката), медиана
пяти последовательных вставок каждого типа после двух разогревочных.

Воспроизведение
---------------
1. Запустить отдельный тестовый экземпляр PostgreSQL 17 на loopback.
   Логину требуется право CREATE DATABASE. Использовать чистый экземпляр:
   существующие базы fridge_bench_* защищены от перезаписи, CREATE DATABASE
   завершится ошибкой. API также использует локальный порт 55438.
2. Из корня репозитория (PowerShell), подставив данные тестового экземпляра:

   $env:PANTRY_BENCH_ADMIN = 'postgresql+psycopg://bench@127.0.0.1:55437/postgres'
   backend/.venv/Scripts/python.exe research/pantry-benchmark/bench.py --requests 240 --repeats 2
   backend/.venv/Scripts/python.exe research/pantry-benchmark/audit.py
   backend/.venv/Scripts/python.exe research/pantry-benchmark/report.py

   Пакеты Python берутся из backend/requirements.txt, дополнительно не нужны.

Артефакты
---------
results/report.txt           вывод и таблица p95 по профилям
results/criteria.json        результаты проверки порогов по конфигурациям
results/metrics.csv          p50/p95/p99, число запросов, ошибки и эффект
results/requests.csv         отдельные HTTP-запросы и их длительность
results/resources.csv        CPU и RAM FastAPI, обращения к блокам PostgreSQL
results/plans/               EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
results/integrity.json       эквивалентность API, журнал, параллельное списание
results/transaction-audit.json контрольные суммы истории, откат, неизменяемость
dataset.py                   генератор воспроизводимой истории
variants.py и projection.sql реализации трёх вариантов
bench.py и audit.py          нагрузочный прогон и сценарии проверки

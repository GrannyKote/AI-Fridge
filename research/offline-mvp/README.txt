Эксперимент AI-Fridge. Список покупок и кладовая при нестабильной сети

Воспроизведение из корня репозитория в PowerShell

  $env:PLAYWRIGHT_CHANNEL = 'msedge'
  $env:PLAYWRIGHT_EXPERIMENT_AUDIT = Join-Path $PWD 'research/offline-mvp/db-audit.json'
  node frontend/app/node_modules/@playwright/test/cli.js test --config frontend/app/playwright.config.mjs offline-experiment.spec.mjs --repeat-each=50 --workers=5 --fully-parallel --max-failures=8 --trace off
  python research/offline-mvp/summarize.py
  Remove-Item Env:PLAYWRIGHT_EXPERIMENT_AUDIT
  node frontend/app/node_modules/@playwright/test/cli.js test --config frontend/app/playwright.config.mjs offline-experiment-conflicts.spec.mjs --workers=1

Нужны зависимости backend/.venv и frontend/app/node_modules, PostgreSQL и
доступный локальный Chromium. Команды создают отдельную схему e2e_<uuid>,
применяют миграции, экспортируют журнал из этой схемы и удаляют только эту
схему. Для локального тестового PostgreSQL можно передать POSTGRES_HOST,
POSTGRES_PORT, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB. Для нестандартных
портов приложения задаются PLAYWRIGHT_API_PORT и PLAYWRIGHT_BASE_URL.
Результаты одного полного запуска должны использовать один экспорт базы.
Во время измерения используется только сценарий offline-experiment.spec.mjs.

Методика

• Один прогон — одна новая группа, 15 записей списка и 5 записей кладовой.
  Остатки меняются с 1 до 6. Все 15 позиций должны перейти в кладовую
  с остатком 1, а прежний открытый список должен стать пустым.
• Состояние приложения подготавливается с подключением. Список открывается
  уже в заданном профиле. Две вкладки одного сеанса позволяют сохранить
  открытую форму расчёта между отметками и изменениями в кладовой.
  Оба варианта используют одинаковый интерфейс. В офлайн-first включается
  штатное локальное хранилище. Для изоляции опыта Service Worker заблокирован.
  Холодный старт, перезагрузка и восстановление после закрытия вкладок
  выходят за рамки измерения. Также не измеряются OCR и рекомендации.
• Стабильная сеть не ограничена. Медленная сеть эмулируется Chromium CDP
  с 400 мс задержки, 400 кбит/с входящего и 100 кбит/с исходящего трафика.
  В прерывистом профиле открытие списка идёт онлайн. Отметки и первые две
  правки выполняются офлайн, третья и четвёртая онлайн, пятая и подтверждение
  офлайн. Связь восстанавливается после попытки подтверждения. Переходы
  привязаны к шагам сценария. В полном офлайне связь отключается перед
  открытием списка и возвращается после окончания или прерывания сценария.
• В знаменателе 21 действие на прогон. Пятнадцать отметок являются
  отдельными действиями интерфейса и подтверждаются флагами is_purchased
  при одной серверной транзакции расчёта. Пять изменений остатка и расчёт
  являются шестью серверными операциями. Открытие списка учитывается
  отдельно. Все запланированные действия остаются в знаменателе, даже если
  открытие списка завершилось ошибкой.
• Успех означает принятие интерфейсом и правильное состояние сервера при
  сверке, дополненное ровно одной записью аудита для данного действия.
  Сверка выполняется через штатные API чтения и триггеры PostgreSQL.
  Успешные ответы с ключом синхронизации дополнительно сверяются с
  таблицей offline_operation. Отметки, относящиеся к одной транзакции
  расчёта, не дублируют число потерянных серверных операций.
• Таймаут ожидания подтверждения UI составляет 6 с. Окно сверки серверного
  состояния составляет 15 с. Потеря в таблице означает отсутствие
  корректного результата для принятой серверной операции к концу окна.
  Такая запись также может означать задержку за пределами окна.
• Отклик UI измеряется в мс от вызова действия Playwright до видимого
  подтверждения. Percentiles nearest rank рассчитаны для полученных
  подтверждений. Отдельно приведены показатели для пяти изменений и
  расчёта, поскольку быстрые локальные отметки влияют на общий процентиль.
• Для профилей с обрывом время после восстановления измерено до
  последнего успешного ответа на принятые изменения. Это наблюдаемая
  верхняя оценка момента фиксации на сервере, включая обратную передачу.
  Без принятых изменений либо при незавершённой сверке значение отсутствует.
  Для профилей без обрыва таблица содержит задержку доставки после
  подтверждения в UI. Если сервер ответил раньше подтверждения UI,
  задержка доставки после подтверждения равна нулю.
• Порог отклика для гипотезы не задан. Показатели задержек приведены
  отдельно от решения по критериям успеха. Стабильная сеть — контроль.

Файлы

  measurements/ — журналы отдельных прогонов.
  db-audit.json — выгрузка триггеров и ключей из схемы теста.
  metrics.csv и metrics.json — сводные результаты.
  conflicts/ — наблюдения отдельных сценариев с конкурирующими операциями.
  db-audit.py и summarize.py — аудит и расчёт сводки.

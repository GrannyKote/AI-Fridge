# AI-Fridge — бэкенд (FastAPI)

API авторизации для дипломного проекта. Работает с локальным PostgreSQL,
схема `diplom_all` базы `diplom`. Таблицы уже существуют, миграции не создаются:
приложение только читает и пишет данные.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Документация Swagger — http://127.0.0.1:8000/docs.

## Настройки

Параметры читаются из `.env` (шаблон — `.env.example`):

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | `postgresql+psycopg://postgres:postgres@127.0.0.1:5432/diplom` | Строка подключения |
| `DB_SCHEMA` | `diplom_all` | Схема с таблицами проекта |

## Эндпоинты

| Метод | Путь | Описание |
| --- | --- | --- |
| `POST` | `/api/auth/register` | Регистрация: создаёт пользователя и его группу |
| `POST` | `/api/auth/login` | Вход по логину и паролю |
| `GET` | `/api/categories` | Категории продуктов из `product_category` |
| `GET` | `/api/units` | Единицы измерения из `unit_of_measurement` |
| `GET` | `/api/products/search?query=` | Первые 5 продуктов из `product` по началу названия |
| `GET` | `/api/groups/{group_id}/products` | Кладовая группы из `user_group_product` |
| `POST` | `/api/groups/{group_id}/products` | Добавить продукт в кладовую |
| `POST` | `/api/groups/{group_id}/products/{item_id}/consumption` | Записать потребление продукта |
| `POST` | `/api/groups/{group_id}/products/{item_id}/waste` | Списать испорченный продукт или пометить запись ошибочной |
| `GET` | `/api/health` | Проверка связи с базой |

Тело запроса для обоих методов авторизации:

```json
{ "login": "ivan.petrov", "password": "secret123" }
```

Ответ:

```json
{
  "id": 1,
  "login": "ivan.petrov",
  "groups": [{ "id": 1, "name": "Новая группа пользователей" }]
}
```

Коды ошибок: `409` — логин занят, `401` — неверный логин или пароль,
`422` — логин или пароль не прошли валидацию, `503` — нет связи с базой.

Тело запроса на добавление продукта (`product_id` передаётся, только если
пользователь выбрал продукт из подсказок):

```json
{
  "name": "Кефир 2.5%",
  "category": "Молочные",
  "unit_id": 5,
  "quantity": 0.5,
  "best_before": "2026-09-01",
  "product_id": 1
}
```

## Логика регистрации

Одной транзакцией (`app/services/users.py`):

1. в `diplom_all.user` добавляется пользователь;
2. в `diplom_all.user_group` создаётся группа «Новая группа пользователей»;
3. в `diplom_all.user_group_user` записывается связь пользователя с этой группой.

Если любой шаг падает, транзакция откатывается целиком.

Кладовая отдаётся уже с названием категории, единицей измерения и остатком
(`remaining` — за вычетом потребления и списаний):

```json
{
  "id": 3,
  "name": "Куриное филе",
  "quantity": 300.0,
  "remaining": 200.0,
  "unit": "г",
  "category_id": 3,
  "category": "Мясо и рыба",
  "best_before": "2026-08-14",
  "is_consumed": false
}
```

## Логика добавления продукта

Одной транзакцией (`app/services/pantry.py`):

1. категория ищется в `product_category` по названию без учёта регистра, при
   отсутствии — создаётся;
2. продукт берётся по `product_id` из подсказки, иначе ищется в `product` по
   названию, при отсутствии — создаётся с найденной категорией;
3. в `user_group_product` записывается строка с количеством, единицей
   измерения и сроком годности.

## Потребление и списание

Оба действия работают одинаково (`app/services/pantry.py`):

1. остаток строки считается как `quantity` минус суммы из
   `user_group_product_consumption` и `user_group_product_waste`;
2. количество больше остатка отклоняется с кодом `422`;
3. пишется строка в `user_group_product_consumption` (потребление) или в
   `user_group_product_waste` (причина «продукт испортился»);
4. пересчитываются флаги строки (`_update_flags`).

Причина «продукт добавлен ошибочно» записей о списании не создаёт — она только
проставляет `is_deleted`.

Флаги в `user_group_product` расставляются так:

| Флаг | Когда ставится |
| --- | --- |
| `is_over` | потребление плюс списания сравнялись с `quantity` |
| `is_consumed` | всё количество ушло в `user_group_product_consumption` |
| `is_wasted` | всё количество ушло в `user_group_product_waste` |
| `is_deleted` | запись помечена ошибочной |

В кладовую попадают строки, у которых не выставлены ни `is_over`, ни
`is_deleted`.

Тело запроса на списание:

```json
{ "reason": "spoiled", "quantity": 100 }
{ "reason": "mistake" }
```

## Демо-данные

Таблицы `product` и `user_group_product` изначально пустые, поэтому кладовая
будет выглядеть пустой. Заполнить её можно скриптом:

```bash
python seed_demo.py                 # пользователь demo / demo123 и 20 продуктов
python seed_demo.py --login ivan    # для уже существующего пользователя
```

Скрипт заводит недостающие единицы измерения и продукты, а список кладовой для
группы каждый раз пересоздаёт. Удалить демо-данные можно так:

```sql
delete from diplom_all.user_group_product;
```

## Структура

```
app/
  main.py             приложение FastAPI, CORS, /api/health
  config.py           настройки из .env
  database.py         engine, сессии SQLAlchemy
  models.py           модели таблиц схемы diplom_all
  schemas.py          схемы запросов и ответов
  routers/auth.py     эндпоинты регистрации и входа
  routers/pantry.py   категории и кладовая
  services/users.py   работа с пользователями и группами
  services/pantry.py  выборка продуктов группы
seed_demo.py          демо-данные для кладовой
```

Обратите внимание: таблица единиц измерения в базе называется
`" unit_of_measurement"` — с пробелом в начале имени. В `models.py` это имя
указано как есть, поэтому SQLAlchemy экранирует его кавычками.

## Важно про пароли

По условию задачи пароли хранятся **в открытом виде** — так их кладёт
`services/users.py` и так же сравнивает при входе. Для реальной эксплуатации
это недопустимо: понадобится хеширование (например, bcrypt через `passlib`)
и выдача токена вместо возврата профиля.

Там же стоит вернуться к доступу: эндпоинты кладовой принимают `group_id`
из запроса и никак не проверяют, что клиент имеет к этой группе отношение.
Появится токен — проверку нужно добавить.

Ещё одно место на будущее: в таблице `user` нет уникального индекса по `login`.
Занятость логина проверяется запросом перед вставкой, поэтому при
одновременных регистрациях теоретически возможны дубликаты. Надёжнее добавить
в базу уникальный индекс:

```sql
create unique index user_login_lower_key on diplom_all."user" (lower(login));
```
